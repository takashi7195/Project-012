## 1. 目的

### 試験環境の一括診断（2026-09-28追加）

利用者が不在でも試験を継続できるよう、専用の補助プログラムでWindows/WSLのツール、Docker/Supabaseの状態、ローカルHTTP経路を一括点検し、共有リポジトリ内へ安全なJSONを保存する。キー値・長さ・生ログ・アカウント名は収集しない。環境変更、サービス再起動、生成API、ホストDB変更は診断に含めない。結果は環境の時点情報であり、権限付与や試験合格の代替ではない。実機の目視・公開判断は引き続き利用者が担当する。

カジュアルな予想サイトとして、対象レースの事実データから、本命・対抗・穴とレース展開をできるだけ表示する。現行の固定採点・固定の買い目構成をAIの判断へ置き換え、レースごとの説明の違いと買い目との整合性を得る。

的中率向上や生成失敗の完全解消を保証するものではない。生成成功率、入力に沿った説明、買い目と文章の整合性、応答時間を確認する。現行の失敗原因がモデルだけにあるとは未確認である。

## 5. 利用者の操作

1. 日本時間の当日の開催情報を読み込む。
2. 利用者が会場・レースを選ぶ。選択だけではAIを呼び出さない。
3. STARTで前回結果を消し、回転とサーバー要求を開始する。
4. サーバーが入力・締切を確認する。同じ入力の成功結果があれば再利用、生成中なら合流、なければ開始する。
5. AIが買い目と展開文を返す。出力不備等があれば残り時間内で1回だけ再試行する。
6. 有効な一組をDBへ原子的に保存する。
7. 各ブラウザーが結果を取得し、既存の停止演出後に対抗・穴・展開文を表示する。

## 6. 入力データ

「全データ」は、対象レースの出走表・直前情報としてDBに保存されたAPI項目全体を指す。全国・当地成績、モーター・ボート成績、F/L、体重、展示、気象、整備・部品等を、存在する範囲で含める。取得していない値を作らない。

結果の実進入・本番ST・確定着順等を展示情報の代用にしない。外部検索やAIの追加データ取得は行わない。上流の事実文字列と生成指示は分離する。

過去10走を別途取得する先行案は撤回済み。全国勝率等、対象レースのAPI項目に含まれる集計値は引き続き渡す。情報の重要度・評価はAIに任せる。

DB内の最新と上流APIの最新が一致する保証はない。5分間隔の収集も、障害時の最大遅延を保証しない。今回、収集処理そのものの頻度や方式は変更しない。

## 7. 出力と検証

- 本命・対抗・穴は、それぞれ1〜6の異なる3艇を着順どおりに持つ。
- 3種類の買い目同士は完全一致させない。同じ艇が別の買い目にも登場することは許容する。
- 展開文は空でない文字列。500文字超、短い文章、1段落・複数段落を理由に失敗にしない。
- プログラムは点数・確率・順位を作らず、買い目を差し替えない。
- 自由文の事実関係・意味上の矛盾を完全には自動検出できない。厳しい推測的な文章検査を加えて生成成功率を下げない。
- 事実にない数値の生成を依頼しない。事実との整合性は比較試験で人が確認する。

JSONの形式、艇番、空欄等の検証と、予想の評価を区別する。JSONの出力項目、日本語、500文字前後という目安、入力データを根拠にする条件は機能に必要な指示として残す。

## 8. 画面と時間

| 項目 | 仕様 |
|---|---|
| 待機中 | 本命は1・2・3。予想値として扱わない |
| 処理中 | START直下に「レース解析中…」。会場・レース・STARTを無効化 |
| 最初の停止開始 | 利用者のSTARTから3秒経過と、保存済み有効結果の取得が両方完了した後 |
| 停止順 | 3着→2着→1着 |
| 次の停止 | 3着停止完了から6秒後、2着停止完了から9秒後にそれぞれ減速開始 |
| 追加結果 | 全停止0.5秒後に対抗・穴・展開文を一緒に表示 |
| 生成待機上限 | 90秒。停止演出は含めない。ネットワークの受信時刻を完全には保証しない |
| 成功 | 状態文を消す。完了時に締切済みなら既存の締切表示 |
| 失敗・再試行可能 | 「予想を生成できませんでした。もう一度お試しください。」 |
| 失敗・再試行不可 | 締切なら「このレースは締切です」。他の無効状態は「予想を生成できませんでした。」 |
| データ取得時刻 | 画面には表示しない |

失敗時は回転を中止し待機の1・2・3へ戻す。対抗・穴・展開文に部分的な結果を残さない。有効な選択は維持する。定期更新が処理中の操作制限を解除しない。正常表示済みの結果は締切だけでは消さない。

## 9. 保存・共有

予想材料、送信時の取得情報、生成設定、使用モデル、指示文版、結果、処理時間を保存する。同じ材料・同じ設定には成功結果を1件に制限する。

取得時刻・DB内ID・最終確認時刻だけの変更で新規生成しない。出走表・展示等の内容変更では別入力とする。モデル、口調、指示文、出力契約、推論設定の変更も別設定とする。

ここで「同じ入力」は予想材料の内容が同じという意味で、取得時刻を含むHTTP送信文面の完全一致ではない。再利用時は最初に生成した予想と、そのとき実際に渡した取得情報を保持する。

最初の利用者の開始から60秒で保存が完了すれば、30秒後に参加した利用者の残り生成待機は約30秒である。後から押した利用者のために最初の90秒を延長しない。入力更新があれば新しい生成として扱い、進行中の古い入力を差し替えない。

## 10. モデルと運用

初期候補は `gemini-3.8-flash`。現行モデルが新方式でも不適切と確定したわけではないため、後続比較に3.5 Flash Lite・3.1 Flash Liteを残す。

利用者提示の無料枠では3.8 Flashは5 RPM／20 RPD、Flash Lite候補は15 RPM／500 RPDだった。これは当該画面の値で、実装時の保証ではない。比較直前に確認する。モデル呼び出し2回の処理は2枠を使用する。保存結果の読取や状態確認ではAI枠を使わない。

別モデルへの自動切替は行わない。変更は運用者の設定変更で行い、入力・設定の識別を維持する。無料枠の上限到達はモデル品質の不合格と分けて評価する。有料枠への自動移行・課金設定変更は含めない。

初回公開の必須試験は3.8 Flashで行う。Flash Lite系との比較は正常動作を確認した後の最適化工程とし、未比較だけを理由に初回公開を止めない。

## 17. 障害切り分け用ログ（2026-09-27、実装前追記）

対象はai_bundle生成とjob読取。既存の買い目・文章・再試行回数・90秒期限を変更せず、入力取得→job取得→AI送信→検証→保存→結果GETの工程を内部ログで追跡する。request IDはサーバーで生成し、job IDと関連づける。公開応答の本文/画面は変えず、診断用X-Request-IDヘッダーだけを付加する。

ログは1行JSONとしてEdgeの標準出力へ記録し、DB障害時にも採取可能にする。既存の専用DBにある試行記録・入力・生成候補は継続利用し、この補強のためのDB migrationは追加しない。HTTP状態、エラー分類、所要時間、試行番号、再試行判断、入力/設定のハッシュを記録する。

APIキー、認証ヘッダー、Cookie、接続文字列、owner token、原始入力・生成文・任意の例外本文/stackは一般ログへ記録しない。既知の項目/値のみを採用する。provider request IDは生値を出さずSHA-256で照合する。

ログ出力の例外は予想へ伝播させず、出力失敗を理由にAIの追加送信を行わない。DB保存が成功したか不明な例外はログで識別し、自動的に保存失敗へ書き換えない。背景処理の未処理例外は安全なログへ変換し、runtimeによる任意の例外本文の流出を抑える。

一つのrequest/workerで共有するログ上限は64行、1行2048 UTF-8 byte。jobのpolling GETは別requestとして上限を持つため、全利用者合計の上限ではない。通常有効、RACE_AI_DIAGNOSTICS=offで無効化できる。これは予想の設定ハッシュに含めない運用設定。

試験ログはGit対象外に置き、公開判断/不具合解消までは保持し、その後30日を整理の目安とする。自動削除は実装せず、プラットフォーム側の保持期間をこの設定で変更できるとは扱わない。Vector再起動中はdocker logsから直接採取し、集約基盤の復旧とは別に可用性を確認する。
