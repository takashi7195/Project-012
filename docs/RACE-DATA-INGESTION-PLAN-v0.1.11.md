# v0.1.11 競艇API → DB格納 実装計画書

作成日: 2026-09-20 JST  
状態: 段階7を実装中。DBスキーマ、手動取り込み、日付キュー、リース、Edge Function、Cron、直近1か月の取り込み、管理用の読み取り検索RPCと追加フィルターを実装済み。停止・復元・容量・検索の受入試験を継続中。公開検索APIとGemini連携は未実装。

## 1. 目的と合意範囲

非公式競艇APIの当日・直近1か月の過去データを保存し、コメント回答、3連単予想、予想検証、将来の別用途から共用できるデータ基盤を作る。特定の質問にだけ対応するテーブル構成にはしない。

今回の対象:

- APIの実データの調査と変換仕様の確定。
- 当日の定期取得、過去日の初回取り込み、欠損・失敗日の再取得。
- 検索用の正規化データ、元JSONの情報、取得履歴・変更履歴の保存。
- 一意性・再実行・訂正・障害復旧・非公開アクセスの検証。
- 将来の自由な検索・集計・予想ができるかを、DBの読み取り試験で確認。

今回の対象外:

- Geminiへの検索ツール追加、AIコメント変更、予想生成、ルーレット変更。
- 公開UI、公開URLの配信内容、既存コメントデータの変更。
- オッズや性別を別の情報源から補う機能。
- 公式サイトの自動収集、的中率改善の主張。

「収集DBが完成した」と「AIがそのDBを参照できる」は別の完了条件とする。

## 3. 実調査で確認したこと

提供元は[boatraceopenapi/api](https://github.com/boatraceopenapi/api)。日付指定URLの5日分を取得した。項目・件数・ハッシュ・取得時刻は[実データ調査記録](research/RACE-API-OBSERVATIONS-20260920.json)、解釈と制限は[調査メモ](research/RACE-API-FINDINGS-20260920.md)に残す。

- 2026-01-01、05-01、09-18、09-19、09-20のHTTP 200を確認。
- 出走表、展示、結果、7賭式の払戻しを確認。
- 最近のデータには `parts`、`propeller`、`remarks`、`refunds`、払戻しの `label` もある。
- 結果オブジェクトが存在しても全着順がnull、払戻しが空配列の場合がある。
- 着順コードには1〜6以外があり、スタート値には負値がある。
- 払戻しの組み合わせがnullで「特払」「不成立」のラベルを持つ行がある。
- 性別、投票前オッズ、発走予定時刻は確認した契約項目にない。締切時刻と混同しない。
- 正常取得した過去日にも、着順が入っていないレースがある。理由は未確定。

更新間隔について、以前の会話で「固定の間隔はない」と説明したが、今回のREADMEには「約3分間隔」の記載がある。ただし更新の保証ではない。当方の5分間隔を足しても最新性の上限は保証できない。

## 4. 初期運用案

すべて設定値とし、収集を有効化するまで外部リクエストは実行しない。

| 対象 | 初期案 | 補足 |
|---|---|---|
| 当日分 | 5分ごと、JST当日の日付URLを取得 | 24時間で最大288回/日。低更新時間帯の縮小は実測後 |
| 昨日分 | 毎日06:10 JSTに再取得 | 結果の遅延・訂正の補完。完全確定と自動断定しない |
| 過去の初回分 | 当日を含む直近30日（当日から29日前まで）。直列で少しずつ | 最初に7日で容量・速度を計測してから30日へ |
| 失敗・欠損の再確認 | 1時間ごとに期限到来分だけ選ぶ | 同じ日を無制限に呼ばない |
| 訂正再確認 | 管理者が指定日を再投入可能 | 保存済み30日分の毎時再取得は行わない |

日付キューを使い、進捗をDBへ保存する。初期上限は外部APIリクエスト同時数1、最低間隔10秒、1 worker呼び出しにつき最大1日。過去分は5分ごとの処理機会に最大1日、当日取得とは開始時刻をずらす。実行枠の調整は提供元の制限と負荷を確認後に行う。

当日・昨日・過去・再試行の同じ日付はまとめて扱う。当日を優先しつつ、過去分の進捗も確保する。日付境界では実行開始時にJSTの日付を確定する。

昨日補完後も不足がある場合の再確認は最大7日間を初期値とし、以後は未解決として残す。過去404も「開催なし」には変換せず、3回まで間隔を空けて再確認し、それでも取得できなければ要確認とする。

## 5. 段階実装と進行条件

各段階は「実装→複数パターン試験→結果確認→次へ」の順で進める。試験結果を記録し、不合格のまま後段を完了扱いにしない。

| 段階 | 作業 | 次へ進む条件 |
|---|---|---|
| 0 | 安定版のGit参照、既存資源一覧、開発先・容量・利用条件を確認 | 安定版に触らず試験でき、実装先が特定できる |
| 1 | API取得・構造検証・正規化を純粋処理として実装 | 5日以上の実データ、null・返還・未知項目等の試験成功 |
| 2 | 新規DBマイグレーション、バージョン管理、索引・権限 | 重複なし、JSON復元、再解析、原子的な公開切替を確認 |
| 3 | 手動の日付取り込みと再実行 | 5日以上を保存し、元JSONと件数・値・集計が一致 |
| 4 | 定期取得、キュー、リース、再試行、停止操作 | 重複実行・プロセス停止・429・DB障害からの復旧を確認 |
| 5 | 7日分の容量測定、当日更新の実観測 | 容量予測が成立し、実更新の記録が得られる |
| 6 | 直近30日を段階取り込み | 全対象日が成功・未提供・要確認などの明示的状態になる |
| 7 | 汎用検索のSQL検証と停止・復元試験 | 管理用検索RPCの代表検索を検証し、結果と残制限を報告 |

段階6の「処理終了」は全日付の全情報が完全に揃うことを意味しない。提供元の欠損は一覧として残す。

## 6. 予定する成果物

- 新しい専用DBスキーマのマイグレーションと限定的な取り消し手順。
- 取得、構造検証、変換、DB書き込みを分離したモジュール。
- 取り込み専用Edge Function、日付キュー、定期実行設定。
- 日付・期間指定の管理用取り込み/再解析コマンド。
- 5日以上の匿名化不要な公開データから必要最小限のテストfixtureとハッシュ。
- 保存内容を照合する検証SQL・試験結果書。
- 運用手順（有効化、停止、再試行、容量確認、バックアップ、復元）。

新しい収集専用の配置先を用い、既存comments用SQLを開発DBへ一括適用しない。ファイル配置とmigration履歴を開発用設定に分離する。旧v0.1.11のmigrationは無検証で再適用しない。

## 7. 受入試験

5件という最低数だけで終えず、以下の組み合わせを試す。現時点で完了しているのは5日分のAPI読み取り調査のみ。DB試験は未実施。

| ID | 試験 | 合格条件 |
|---|---|---|
| T01 | 異なる5日・複数会場の取り込み | 日付/場/R/枠が一致し、元の各件数と照合できる |
| T02 | 同じJSONを2回取り込み | 正規化行・履歴が増殖せず、取得履歴だけ増える |
| T03 | 同じ日の2 worker並行実行 | 有効な書き込みは1件。古いリースのworkerが公開できない |
| T04 | 原本復元 | manifestと構成要素から復元したJSONが意味的に元JSONと一致 |
| T05 | 出走表→展示→結果 | 各時点が保持され、結果前の版に結果が混入しない |
| T06 | 空の結果枠 | 結果取得済みと誤判定せず、未提供/未確定を区別可能 |
| T07 | null・0・空配列・項目不存在 | 4者の区別が元データから復元可能 |
| T08 | 負のST、特殊着順 | 負値を拒否せず、コード14を14着と解釈しない |
| T09 | 同着・複勝・拡連複 | 同賭式の複数払戻しを欠落させない（未観測ケースは人工fixtureと明記） |
| T10 | 特払・不成立・返還 | null組み合わせを保持、通常の的中配当と分離 |
| T11 | 取得済み結果が後続で空になる | 観測は記録、良好版を保持し、後退・古さの状態が伝わる |
| T12 | 金額訂正・選手訂正 | 新版に訂正反映、旧版が保持される。過去年齢が変わらない |
| T13 | 未知の項目・賭式・型の変更 | 未知情報を原本に保持。不正型は隔離、黙って欠落させない |
| T14 | 404・429・5xx・タイムアウト | 有限再試行、Retry-After尊重、良好版保持、原因コード記録 |
| T15 | 保存途中のDB障害 | 未完成版が検索側に見えず、再実行で完了する |
| T16 | JWT/APIキー/専用認証なしの呼び出し | 非公開データと取込処理へ匿名アクセスできない |
| T17 | 日付境界・UTC/JST | 前日と当日の取り違えがない。締切が+09:00で一致 |
| T18 | 最高払戻し | 全賭式/3連単別の最大値と同額首位を元JSON集計と照合 |
| T19 | 選手検索・最年少・出走数 | 登録番号、開催時点年齢で正確に照合。欠場を出走実績と混同しない |
| T20 | データ範囲の欠損 | 集計結果に欠損日・未確定・coverage根拠を伴う |
| T21 | 再解析 | 同じ原本を新parserで処理し旧版・出所を追跡可能 |
| T22 | 容量・実行時間 | 7日分の索引込み実測、30日分の予測、worker予算を確認 |
| T23 |停止・再開 | 新規取得停止、処理中の収束、再開位置を確認 |
| T24 | バックアップ復元 | 新しい空の開発DBへ復元し件数・ハッシュ・検索結果が一致 |
| T25 | v0.1.10保全 | main/tag・公開コード・本番接続設定に変更なし |

5月1日の結果が空のレースの理由が確定するまでは、「全国最高の公式結果」とする検証は行わず、「取得済みデータ内の最大値」と元JSON集計の一致を検証する。

## 8. 容量と費用の判断

約1.5MBを5分ごとに全文重複保存すると、概算で432MB/日、約13GB/30日になる。これは比較用の単純計算であり、採用構成の実容量ではない。

採用構成は変化した出走表・展示・結果だけを履歴化し、同じ内容は再利用する。古い日付は原則初回1回の取り込み。JSONB・索引・履歴の実容量はサンプル保存で測る。未測定の段階で無料枠に収まるとは約束しない。

初期方針: レース事実と元情報の履歴は自動削除しない。運用ログは30日を初期案とし、長期の件数・成功状況は日別に保持する。容量70%で通知、85%で過去取り込みを停止、95%で新規書き込みを安全停止する案を、実契約容量に合わせて設定する。容量不足を隠すための自動削除はしない。

30日取り込み前に、対象DBの空き容量、7日分実測、30日分の予測増加量を報告する。追加課金・保存期間短縮が必要なら、その具体的な選択を相談する。

## 9. 実装・運用上の残課題

- 開発用Supabaseプロジェクトの準備可否、接続先と権限、容量・費用。
- 提供元の明示的なアクセス制限等。記載がない項目は「制限なし」と見なさない。
- 性別・投票前オッズ・公式確定フラグ・完全な開催一覧はこのAPIだけで保証できない。
- APIの締切前公開時刻は不明。過去JSONは当時利用可能だった情報の証明にはならない。
- 30日を超える長期履歴の容量実測。無料枠で直近30日と当日履歴を保存できるかは7日分の実測後に確定する。
- Project-012ではVault拡張が利用できないため、Cron用秘密の保管方式はVault利用可能時に移行する。

DBマイグレーション、Cron、Edge FunctionはProject-012へ適用済み。直近30日の取り込み、容量・復元・障害試験、AIからの読み取り連携は未完了である。既存の30日より古い保存済みデータは削除せず、今回の範囲外として残している。HISTORY.mdには実装段階の変更を記録する。
