## 4. 一件ごとの手順と障害対応

1. ケースIDと不足条件を選び、時刻・対象ソース/runnerのSHA-256・接続先を記録。HEADだけで未コミットの対象を識別しない。
2. fixtureと片付けを確認して実行し、終了コード・期待結果・実測を照合。秘密値や生ログは保存しない。
3. 失敗は環境、試験プログラム、製品、外部サービス、仕様不明へ切り分ける。根拠がない箇所は未特定とする。
4. 再実行前に新しい仮説または変更点を書く。新しい証拠を得られない同条件の再実行を続けず、外部待ちの項目はblockedとして独立項目へ進む。
5. 修正を設計と照合し、該当試験と影響する回帰を確認。mock成功を実Edge/実Gemini成功の代用にしない。
6. 自分が作成したfixture/一時資源だけ片付け、残存を確認。成績書を更新し次へ進む。報告だけのために実行可能な試験を中断しない。

既知事項: VectorはrestartingだがDocker直接ログ採取は成功。管理API認証成功だけでは、ホスト検証先の識別や全操作権限は確定しない。

## 5. 作業範囲と利用者への依頼

自律実行はローカル試験、設計に沿う修正/再試験、読み取り診断、成績更新を行う。既存DB全体のresetや無関係な資源の削除は行わない。HISTORY.mdは明示指示なしに変更しない。

認証確認から本番デプロイ・push・課金変更への指示を推定しない。実施指示が既にある場合はその範囲に従う。ホストへのfixture投入は検証先を確定してから行う。

利用者が必要なのは、実機/目視、未決の接続先や費用上限の判断、避けられないPC/認証の対話操作。依頼には理由と期待結果を添え、PowerShellへ貼れる1行を示す。結果は共有ファイルから読み、秘密値や長い出力の転記は求めない。依存しない試験は継続する。
